# 업무요약 통합 및 상세 기능 연결

문서 버전 v1.0 / 2026-11-12 / 기준 커밋 8c4768e (PR #2)

## 변경 목적

구매기업 사용자가 두 종류의 요약 화면을 오가던 구조를 정리합니다. 팀원이 디자인한 기업 대시보드를 기본 화면으로 사용하고, 기존 콘솔의 상세 업무를 필요한 위치에서 바로 엽니다. 소개 페이지와 계산 산식은 변경하지 않습니다.

```text
기업 로그인 / 기존 app.html 및 #/dashboard 진입
                       ↓
           my.html — 업무요약 한 곳
             ├─ 자료 보완 → app.html#/review
             ├─ 발주 미반영 → app.html#/reconcile
             ├─ 계약 갱신 → app.html#/contracts/ST-005
             ├─ 자료·제출 → app.html#/requests 또는 #/packages
             └─ 약정 상세 → app.html#/contracts/{약정번호}
                       ↑
             상세 화면의 기업 대시보드 링크
```

공급기업 체험은 `#/supplier`에서 자사 거래를 표시합니다. 구매기업으로 전환하면 약정 목록으로 이동합니다. 지급 시뮬레이션은 별도 링크로 유지하며 실제 송금과 연결하지 않습니다.

## 수정 내용

| 영역 | 변경 |
|---|---|
| 기업 대시보드 | 홈 명칭을 업무요약으로 통일, 각 처리 업무에 상세 링크, 상세 업무 바로가기 추가 |
| 요청 처리 | 기존 요청 안내 유지, 요청 후 후속 업무 링크와 바로가기 주소를 공통 함수로 관리 |
| 상세 라우팅 | 구매기업 운영요약 제거, 기본·이전 요약·알 수 없는 주소는 기업 대시보드로 연결 |
| 공급기업 | 자사 요약 유지, 자사 조회 메뉴와 구매기업 전용 메뉴 구분 |
| 약정·자료 탭 | 계약 상세 검토와 공유 이력·패키지 상세 연결 |
| 상태 복귀 | 브라우저 뒤로가기로 돌아왔을 때도 대시보드가 현재 가상 상태를 다시 읽도록 pageshow 처리 |
| 협업 문서 | 과거 인수인계는 보존하고 현재 실행·리뷰 방법을 docs/README.md로 안내 |

신규 파일: `src/detail-navigation.ts`, `src/detail-navigation.test.ts`.
주요 변경 파일: `src/main.ts`, `src/views/dashboard.ts`, `src/my/` 화면 파일, `src/types.ts`, `my.html`, `app.html`.
패키지·잠금 파일·Vite·TypeScript·GitHub Actions 설정은 변경하지 않았습니다.

## 검증 결과

- 팀의 package-lock.json 그대로 `npm ci` 실행.
- 기본 네이티브 Rollup 구성에서 `npm run check` 통과: 규칙·타입·테스트 20개·Vite 빌드.
- 신규 테스트 6개: 과거/기본/알 수 없는 경로, 계약 ID, 공급기업 경로, 잘못된 인코딩, 업무별 연결 주소.
- 브라우저 확인: 단가 반영 요청 → 처리 대기 → 반영 대조 → 수정 발주 반영 → 대시보드 복귀.
- 발주 반영 후 미반영 1→0건, 처리할 업무 3→2건 확인.
- 신규 약정 검토·자료 공유·제출 패키지 화면 이동 확인.
- 공급기업 자사 현황 표시 및 구매기업 전환 시 약정 목록 진입 확인.
- 기본 app.html / 과거 #/dashboard가 my.html로 이동함을 확인.
- 1440px 데스크톱 및 390px 모바일 화면 확인. 모바일 대시보드 문서 폭 375px와 내용 폭 375px로 페이지 가로 넘침 없음. 상세 계약 모바일 메뉴는 내부 가로 스크롤을 유지.
- 지급 시뮬레이션 화면 진입과 동의·예치 전 지급 비활성 상태 확인. 지급 완료·중복 실행 최종 확인은 브라우저 연결 시간 초과로 완료하지 못함. 이번 변경에서 지급 로직은 변경하지 않음.

## WASM 변경에 대한 설명

이전 PR #1에서 Windows 보안 정책에 의해 Rollup 네이티브 모듈 실행이 차단된 환경을 해결하기 위해 공식 WASM 구현을 사용했습니다. 직접 의존성 별칭과 overrides로 하위 의존성도 통일했으며 서비스 기능상 필요한 변경은 아니었습니다.
개인 환경의 해결책이 공용 빌드 설정까지 영향을 미치는 변경이었으므로 PR #2에서 제외한 결정을 따릅니다. 이번에는 팀의 기존 설정으로 설치와 검사가 통과했으며 WASM 교체는 재도입하지 않았습니다. 이전 정책 차단의 해제 원인은 이번 작업에서 확인하지 않았습니다.

## 검토 및 후속 작업

1. 팀원은 새 업무요약 디자인과 상세 링크 위치를 확인합니다.
2. 신규 검토·패키지·공급기업 화면의 업무 적합성과 시뮬레이션의 최종 클릭을 확인합니다.
3. 변경 요청은 PR 댓글로 남기고 같은 작업 브랜치에 반영합니다.
4. 리뷰 완료 후 main 병합 및 Actions 배포 성공을 확인합니다.

기존 잠금 파일 설치에서 npm audit 경고 5건(중간 2·높음 1·심각 2)이 표시됐습니다. 이번 화면 통합 범위에서 의존성이나 보안 설정을 임의 변경하지 않았으며 개발 담당자의 별도 패키지 검토가 필요합니다.
이 문서는 구현 및 검증 기록입니다. 실제 AI·ERP·서명·송금·서버 권한이 구현되었다는 의미는 아닙니다.
