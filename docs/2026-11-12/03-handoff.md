## 8. 팀원이 직접 확인할 시연·QA 순서

아래 항목은 다음 수동 확인을 위한 절차이며 모두 완료됐다는 기록이 아니다. 가상 시나리오만 사용한다.

### 시나리오 A — 기존 약정과 요청 대기

1. 시작 전 데모 초기화 버튼으로 가상 진행 상태를 초기화한다.
2. /start.html?path=A에 접속해 가상 회사 정보로 진행한다.
3. 약정 불러오기 후 확인 가능한 항목을 표시한다.
4. 적용일이 미확정인 동안 다음 단계로 넘어가지 않는지 확인한다.
5. 원문 발췌와 가상 보완합의서를 확인해 적용일을 확정한다.
6. 초대는 나중에, ERP는 가상 매핑 또는 나중에 연결을 선택한다.
7. 완료 후 AL-001 조건과 내 업무 화면을 확인한다.
8. C-102 수정 요청을 기록한다. “ERP 반영 대기” 상태로 남아야 한다.
9. /app.html#/reconcile에서 발주 → 청구 → 지급근거를 순차 반영한다.
10. 내 업무·증빙 요약에 같은 상태가 보이는지 확인한다.

### 시나리오 B — 신규 검토

1. /start.html?path=B에서 신규 검토로 이동한다.
2. 처음에는 AL-004가 초안이고 적용 법률·기업 규모가 추가 검토 대상임을 확인한다.
3. 투입량 4를 입력해 원재료비 11,200원, 비중 약 50.9%가 나오는지 확인한다.
4. 빈 값·음수·비정상적으로 큰 값을 입력했을 때 오류를 확인한다.
5. 계산 뒤 값을 바꾸고 바로 승인하면 재계산 안내가 나오는지 확인한다.
6. 원문 대조·공유 범위·구매기업·공급기업 확인을 모두 선택한다.
7. 데모 승인 후 약정·대시보드·증빙 요약에서 AL-004 상태 변경을 확인한다.
8. 새로고침 후 확정 상태가 유지되는지 확인한다.

### 시나리오 C — 역할과 출력

1. 구매기업·공급기업 역할을 전환해 헤더 회사명이 바뀌는지 확인한다.
2. 공급기업은 AL-001과 RQ-08 등 자사 범위만 보이고 AL-004·다른 회사 요청은 보이지 않아야 한다.
3. 공급기업에서 자사 외 계약 주소로 이동하면 접근 안내가 보여야 한다.
4. 구매기업·공급기업 각각 CSV를 내려받아 열 개수, 한글, 금액, 포함 계약을 확인한다.
5. 인쇄 미리보기에서 메뉴가 빠지고 증빙 요약만 출력되는지 확인한다.
6. A4 가로 PDF로 저장해 표 잘림·줄바꿈·페이지 구성을 확인한다.

### 시나리오 D — 지급 시뮬레이션

1. 초기 상태에서 실제 체인 미연결 문구를 확인한다.
2. 예치 전 또는 명세 미확인 상태에서는 지급이 실행되지 않아야 한다.
3. 가상 예치와 명세 확인 후 지급을 실행한다.
4. 완료 뒤 재실행 버튼이 비활성화되는지 확인한다.
5. 새로고침 후 완료 상태가 유지되는지 확인한다.
6. 이 시뮬레이션으로 반영 대조의 payment가 바뀌지 않는지 확인한다.

### 화면·접근성 확인

- 1440px 데스크톱, 900px 경계, 390px 모바일 폭에서 레이아웃 확인.
- 모바일 메뉴·넓은 표가 페이지 전체를 과도하게 가로 확장하지 않는지 확인.
- 처리 시트를 열고 Tab·Shift+Tab·Escape·포커스 복귀 확인.
- 브라우저 뒤로가기·새로고침·동일 origin의 다른 탭 상태 변경 확인.
- 브라우저 저장 제한·저장 공간 부족 시의 오류 안내 확인.

## 9. 현재 남은 작업과 다음 우선순위

### 9.2 실제 서비스로 확장할 때의 순서 제안

1. 계약·품목·버전·기간·계산·발주·청구·지급근거를 식별하는 데이터 모델 확정.
2. 고정 ID·전역 boolean을 계약별·기간별 상태로 전환. 현재 po/invoice/payment는 AL-001 전용이다.
3. 서버 인증·테넌트 격리·문서별 권한·비공개 파일 저장·열람 로그 구현.
4. 합성문서 업로드와 실제 파일 파싱·검증, 출처 좌표·페이지 연결 구현.
5. LLM 추출과 규칙 기반 법률 검토·계산 엔진의 인터페이스 분리. 법률 적용 결과는 근거 버전과 담당자 검토를 연결.
6. 단위·부가세·반올림·스크랩·소요량·적용일·취소 건 등 실무 산식 규칙 확정 및 정답셋 검증.
7. 요청·회신·양사 확인·갱신·이의제기를 실제 사용자별로 처리.
8. ERP 파일 입출력부터 실증하고 필요할 때 API로 확장.
9. 목적별 증빙 템플릿과 실제 원문 첨부·승인 범위·출력 기능 구현.
10. 업무 데이터가 안정된 뒤 별도 Kairos 테스트넷 실증. 지급명세 ID·버전·승인 권한·중복 실행·취소·재발급·자금 부족·수수료·트랜잭션 실패를 검증.

이 순서는 후속 제안이다. 실제 착수 범위·일정·담당자와 프로덕션 체인은 팀이 정한다. 이번 문서로 대구체인·메인넷·고객 자금 운영을 승인한 것은 아니다.

## 10. 다음 AI에게 전달할 작업 규칙

### 반드시 유지할 원칙

- 먼저 저장소의 AGENTS.md와 CLAUDE.md를 읽는다.
- Vite + TypeScript 구조를 유지한다. 프레임워크 전환은 별도 합의 없이 수행하지 않는다.
- 함수는 화살표 함수, 명시적 매개변수·반환 타입, 공통 타입은 src/types.ts를 사용한다.
- any, console.log, 불필요한 가변 객체 변경을 피한다.
- HTML 동적 데이터는 esc(), 금액은 won(), 퍼센트는 pct()를 사용한다.
- 파일을 400줄 이내로 유지하고 큰 기능은 모듈로 나눈다.
- 실제 회사·사람·기밀·키를 예시 데이터로 넣지 않는다. 회사는 (가상) 표기를 유지한다.
- 요청 전송 ≠ 반영 완료, 계산액 ≠ 지급 실적, 시뮬레이션 ≠ 온체인 거래를 유지한다.
- 적용 대상 검토 초안 ≠ 최종 법률 판단, 서비스 산출표 ≠ 전문기관 확인서를 유지한다.
- 공급기업 필터 ≠ 실제 서버 보안, localStorage ≠ 공동 DB, 클릭 확인 ≠ 전자서명을 구분한다.
- 수정 후 npm.cmd run check를 실행한다. 계산 규칙 변경 시 calc.test.ts도 보강한다.
- public/CNAME과 상대 경로 링크를 유지한다.
- 변경 파일을 덮어쓰거나 초기화하지 말고, 현재 미커밋 변경과 팀원의 추가 변경을 먼저 확인한다.
- main으로 직접 푸시하지 않는다. 브랜치·PR·팀 검토 후 반영한다.

## 11. 이 문서의 근거와 사용 방법

- 변경 전후 근거: 현재 작업 트리와 HEAD b433185 대비 diff, 신규 파일 본문.
- 검증 근거: 직전 구현 작업에서 반환된 npm run check 결과와 로컬 HTTP 응답.
- 이번 작성 범위: 코드·Git 상태 재확인과 인수인계 문서 생성. 정책·법률·시장 수치의 신규 조사나 웹사이트 코드 추가 수정은 수행하지 않았다.
- 팀원은 1~4절을 먼저 읽고, 개발 담당자와 AI는 5~10절까지 읽는다.
- 가상 승인·기관 증빙·온체인 지급 설명을 외부에 발표할 때는 구현 수준을 그대로 표시한다.
- 실제 작업본이 바뀌면 문서 버전과 아래 스냅샷을 함께 갱신한다. 파일 해시는 시점 확인용이며 보안 인증이나 블록체인 기록이 아니다.
