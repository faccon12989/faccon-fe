## 1. 먼저 읽을 핵심 요약

이번 작업의 중심은 “서비스가 무엇을 해주는지 보여주는 화면”을 “가상 거래의 업무 상태를 따라갈 수 있는 데모”로 개선하는 것이다.

- 요청을 보냈다는 이유만으로 업무를 완료하지 않는다. 실제 반영·보완 여부와 요청 상태를 구분한다.
- 기존 약정을 운영하는 A 경로와 신규 약정을 검토하는 B 경로를 연결했다.
- 자료 출처 확인 → 누락값 보완 → 고정 산식 계산 → 공유 범위·양사 확인 → 운영 화면의 흐름을 추가했다.
- 조정 계산액, 발주 반영, 청구 일치, 지급근거를 따로 보여준다.
- 공급기업 역할에서는 자사 계약·자료 요청·열람 이력·증빙 요약만 보이도록 화면 필터를 수정했다.
- 화면에서 확인한 증빙 요약을 실제 CSV 파일로 내려받거나 브라우저 인쇄 기능으로 PDF 저장할 수 있게 했다.
- 블록체인 화면은 실제 체인 연결 없는 지급 시뮬레이션으로 명시했다.
- 일부 가상 상태를 localStorage로 공유해 내 업무와 운영 화면이 같은 결과를 읽게 했다.

중요한 구현 수준: 현재는 프런트엔드 데모다. 실제 고객 로그인, 서버 DB, 비공개 파일 저장소, AI API, ERP API, 전자서명, 정부기관 제출, 스마트컨트랙트 배포·송금은 이번 작업에서 구현하지 않았다.

## 2. 서비스 기획과 이번 수정의 관계

서비스 주제는 “단가 조정 효율화 서비스”다. 구매기업이 여러 공급기업의 거래를 관리하면서 연동약정 조건을 검토하고, 약정에 따라 계산된 단가가 발주·청구에 반영됐는지 확인하며, 근거를 제출 가능한 형태로 정리하는 업무를 돕는다.

이번 수정에서는 다음 원칙을 화면에 반영했다.

1. LLM의 역할은 문서에서 항목·출처를 찾고 보완사항을 정리하는 것이다. 금액 계산은 명시적인 계산 프로그램이 담당한다. 현재 LLM 역할은 가상 추출 결과로 표현한다.
2. 원재료 비중만으로 연동제 의무 대상 여부를 확정하지 않는다. 적용 법률·기업 규모·거래 유형·예외 사유 확인이 필요한 검토 초안으로 안내한다.
3. 약정 조건 자체를 확정하거나 변경하는 확인 절차와, 이미 약정된 산식에 따라 매달 계산하는 절차를 구분한다.
4. 구매기업이 서비스 비용을 지불하더라도 공급기업 원가 원문에 대한 포괄적 열람 권한을 얻는 구조로 설명하지 않는다.
5. 정부기관 증빙은 계산·반영·지급 상태와 근거 문서의 연결을 보여준다. 서비스 이용만으로 기관 인증·포상·가점이 발생한다고 표시하지 않는다.
6. 블록체인은 본 업무와 구분한 차액 지급 실증의 확장 방향으로 다룬다. 이전에 논의한 제조기업 매칭·금융기관 연결·토큰 발행을 이번 웹사이트의 구현 완료 기능으로 되돌려 넣지 않는다.

기존 약정의 반복 운영을 초기 진입 경로로 유지하면서 신규 검토 체험을 보강한 것이다. 새로운 고객군·가격·법률 해석을 팀의 확정 결정으로 추가한 것은 아니다.

대표 흐름은 두 갈래다.

```text
A. 기존 약정
소개 → 가상 약정 불러오기 → 추출값·적용일 확인
     → 등록 설정 완료 → AL-001 약정 확인
     → 수정 요청 기록 → 발주 반영 → 청구 확인 → 지급근거 확인
     → 현재 상태를 담은 증빙 요약 출력

B. 신규 약정
소개 → 신규 검토(AL-004) → 가상 자료 출처 확인
     → 투입량 보완 → 산출표 초안 계산
     → 원문 대조·공유 범위·양사 확인(모두 데모)
     → 운영 중 약정으로 전환 → 약정·대시보드·증빙 요약에 반영
```

B 경로 완료가 A 경로의 AL-001 발주를 변경하지 않는다. 현재는 서로 다른 고정 가상 계약으로 두 가지 업무 흐름을 보여준다.

## 4. 우선순위별 상세 변경내역

### 4.1 P0 — 요청을 완료로 처리하던 문제 수정

변경 전: 내 업무의 처리 시트 마지막 단계까지 누르면 요청 종류와 실제 처리 여부에 관계없이 할 일을 완료 목록으로 옮겼다.

변경 후: 요청 내용은 저장하되 후속 근거가 없으면 대기 상태로 남긴다. 요청 중이라는 사실이 내 업무와 운영 현황에 함께 표시된다.

| 업무 ID | 업무 | 요청 뒤 상태 | 현재 완료 판정 |
| --- | --- | --- | --- |
| C-101 | ST-005 갱신 검토 | 선택에 따라 갱신본·서명 / 잔여 발주 / 담당자 회신 대기 | 최종 갱신·종료 완료 처리 미구현 |
| C-102 | AL-001 단가 미반영 | ERP 반영 대기 | 가상 발주 반영 상태 po=true |
| C-103 | AL-004 자료 보완 | 보완자료 회신 대기 | 신규 약정 데모 확인 완료 draftApproved=true |

C-101의 “연장했어요 / 거래를 끝냈어요 / 잘 모르겠어요”는 각각 다른 대기 상태로 분기한다. 거래 종료를 선택했다고 남은 발주가 취소되거나 계약이 즉시 종료되는 것은 아니다.

받는 담당자·회신 기한 선택도 요청 기록에 담는다. 실제 메일을 발송하는 기능은 없다. C-102 완료는 발주 반영 완료를 뜻하며 청구·지급 완료를 뜻하지 않는다.

관련 코드: src/demo.ts의 requestTask, taskStatus, taskDone / src/my/my.ts의 advance / src/my/screens.ts / src/views/dashboard.ts.

### 4.2 P0 — 초안·종료 약정·운영 중 약정의 구분

변경 전: AL-004처럼 투입량이 미확정인 초안에서도 계산된 숫자가 이번 달의 적용 단가처럼 보일 수 있었다.

변경 후:

- 초안 상세는 “투입량 보완 및 양사 확인 전” 안내와 검토 화면 링크를 우선 표시한다.
- 내 약정의 초안은 “준비 중”으로 표시한다.
- 종료 약정은 “종료·갱신 검토”와 “참고 단가”로 표시한다.
- 내 업무·운영 현황의 금액 합계는 status=ok인 운영 중 약정만 대상으로 한다.
- 증빙 요약에서 초안·종료 약정의 확정 계산값과 차액은 집계에서 제외한다.

단, 운영 현황의 계약별 개별 행은 초안 참고 차액도 보여준다. 합계에서 제외되는 것과 모든 화면에서 숫자가 완전히 숨겨지는 것은 다르다. 후속 개발 시 상태 표현을 일관되게 유지한다.

관련 코드: src/my/screens.ts / src/views/contracts.ts / src/views/dashboard.ts / src/evidence.ts.

### 4.3 P0 — 지표 변동률과 제품 단가 변동률 구분

기존에는 원재료 지표 +8%가 제품 단가 +8%처럼 읽힐 수 있었다. 이번에는 지표 배지와 단가 표시를 분리했다.

AL-001 예시:

```text
기준 제품 단가 P0 = 10,000원/개
제품당 원재료비 M0 = 4,000원/개
기준 지표 I0 = 100, 비교 지표 It = 108
원재료 지표 변동률 = +8.0%
조정 요건 = ±5% 이상 → 충족

조정 단가 = 10,000 + 4,000 × (108 - 100) / 100
          = 10,320원/개
제품 단가 변동률 = 320 / 10,000 = +3.2%
1,000개 기준 조정 차액 = +320,000원
```

계산 알고리즘 자체는 이번 작업에서 바꾸지 않았다. 조건 충족 시에만 기존 산식을 적용하고 최종 단가를 원 단위로 반올림하는 src/calc.ts를 계속 사용한다.

조정 차액은 기업 간 거래금액의 변화다. 구매기업의 비용 절감액이나 실제 송금액으로 표현하지 않는다.

### 4.4 P0 — 발주·청구·지급근거 대조 개선

변경 전: 완료된 조건의 개수를 합산해 진행 막대를 채웠다. 뒤 단계가 일치하면 앞 단계의 불일치까지 완료처럼 보일 여지가 있었다. 청구단가도 표에서 직접 비교하기 어려웠다.

변경 후:

- 계산단가, 발주단가, 청구단가를 별도 열로 표시한다.
- 산출 상태, 발주 일치, 청구 일치, 지급근거를 각각 boolean으로 판정한다.
- 발주 불일치 / 청구자료 대기 / 청구 불일치 / 지급근거 대기 / 대조 완료를 구분한다.
- 종료 약정은 갱신 검토를 우선 안내한다.
- AL-001에 가상 반영 버튼을 넣었다. 버튼을 누를 때마다 발주 → 청구 → 지급근거 순으로 상태가 바뀐다.

```text
초기: 계산 10,320원 / 발주 10,000원 / 청구 없음 / 지급근거 없음
  ↓ 수정 요청 기록
ERP 반영 대기 — 아직 완료 아님
  ↓ ① 수정된 발주 파일 반영(가상)
발주 10,320원 / 청구자료 대기
  ↓ ② 청구 파일 반영(가상)
청구 10,320원 / 지급근거 대기
  ↓ ③ 지급근거 확인(가상)
AL-001 대조 완료
```

버튼은 가상 상태 전환이다. CSV 원문을 읽어 실제 매칭하거나 ERP 데이터를 수정하는 기능은 아직 없다. 현재 지급근거 확인도 실제 은행 거래를 조회하는 동작이 아니다.

관련 코드: src/demo.ts의 demoRows, reconcileChecks, nextEvidence / src/views/operations.ts / src/main.ts.

### 4.5 P0 — 역할별 회사명·자료·이력 표시 수정

### 4.6 P1 — 기존 약정 등록 A 경로 보완

기존 6단계 화면을 유지하면서 시연을 막거나 오해를 부르는 부분을 조정했다.

3. 추출 신뢰도가 낮은 적용일을 전체 확인 버튼으로 무조건 승인할 수 없게 했다. 0.8 미만 항목은 별도 보완이 필요하다. 이 값은 예시용 UI 기준이지 학습·평가로 검증된 AI 정확도 기준이 아니다.

5. 보완합의서 확인 버튼은 적용일을 “익월 1일 이후 검수분”으로 정리한다.
6. 공급기업 초대는 나중에 할 수 있다. 구매기업의 공유 범위 선택만으로 원문을 공개하지 않으며 상대방 승인이 필요하다고 설명한다.

9. 마지막 버튼은 “파일럿 시작” 대신 “데모 설정 저장”이다. 완료 화면에서 실제 초대·상담 신청이 이루어지지 않는다고 안내한다.
10. 완료 시 setup=A만 공유 저장소에 저장하고 AL-001 약정 화면으로 연결한다.

현재 A 경로는 미리 준비된 AL-001의 등록 절차를 체험한다. 회사명·이메일·초대 목록·ERP 매핑·추출 확인값 전체를 DB나 localStorage에 영구 저장하는 기능은 아니다.

고객이 이미 확보한 전문가 검토 결과를 가져오는 방향으로 설명을 정리했으며, 전문기관 중개·소개 서비스를 새로 구현하지 않았다.

### 4.7 P1 — 신규 약정 B 경로 추가

start.html?path=B 또는 시작 방식에서 신규 준비를 선택하면 app.html#/review로 이동한다. 신규 모듈은 src/views/review.ts다.

이 화면은 AL-004의 검토 절차를 네 부분으로 설명한다.

**① 제출자료에서 확인한 사실과 미확인 항목**

- 가상 계약금액 132,000,000원, 거래기간 120일, 원재료 매입 단가 2,800원/kg를 출처와 함께 표시한다.

- 적용 대상 여부는 “추가 자료 필요”로 표시한다. 실제 법률 규칙 엔진이 결론을 내리는 화면은 아니다.

**② 누락된 투입량 입력과 산출표 초안 계산**

```text
가상 원문: 제품당 알루미늄 4kg
4kg × 2,800원/kg = 제품당 원재료비 11,200원

```

빈 값·0 이하·유효하지 않은 숫자를 거부한다. 이 단순 예제에서는 원재료비가 납품단가를 넘는 입력도 거부한다. 마지막 조건은 실무의 보편적 법칙이 아니라 데모 계산 범위를 제한하는 장치다.

**③ 원문 대조·공유 범위·양사 확인**

- 원문과 투입량·단위를 대조했다는 확인
- 공급기업의 산정 결과 공유 범위 확인
- 구매기업의 조건 확인
- 공급기업의 같은 조건·버전 확인

위 네 항목과 재계산 여부를 점검하고 승인 상태를 저장한다. 화면에서 하나의 사용자가 양사의 역할을 체험하므로 실제 양사 인증·전자서명은 아니다.

**④ 운영 화면 반영**

- draftApproved=true 및 draftM0 저장
- AL-004 상태가 draft에서 ok로 변경
- 버전이 v1.0 (데모 승인)으로 표시
- 저장한 원재료비가 약정 계산·대시보드·증빙 요약에 반영

원가자료 입력 영역은 공급기업이 보는 검토 절차의 예시라는 설명을 덧붙였다. 실제 서비스에서는 공급기업 입력 영역과 구매기업 공유 결과 영역을 서버 권한 기준으로 나눠야 한다.

### 4.9 P1 — 페이지 간 가상 상태 공유

기존 페이지별 메모리 상태를 일부 공통 모듈로 옮겼다. 저장 키는 faccon-demo-v2다.

```text
data.ts의 가상 원본
       +
localStorage의 가상 진행 상태
       ↓
demoContracts() / demoRows() / taskStatus()
       ↓
내 업무 · 약정 · 운영 현황 · 반영 대조 · 증빙 요약
```

이 상태는 같은 브라우저·같은 origin에서만 공유된다. localhost와 127.0.0.1, 다른 포트, 공개 도메인은 서로 다른 저장 공간이다. 서버 동기화나 여러 직원 간 협업 저장이 아니다.

현재 저장하는 정보:

| 필드 | 의미 | 적용 범위 |
| --- | --- | --- |
| version | 저장 스키마 버전 2 | 파싱 검증 |
| requests | 요청 ID·선택·상세 내용 | C-101~103의 대기 상태 |
| po | 가상 발주 반영 | AL-001 |
| invoice | 가상 청구 반영 | AL-001 |
| payment | 가상 지급근거 확인 | AL-001 업무 대조 |
| setup | A/B/null | 등록 완료 경로 |
| draftApproved | 신규 약정 데모 확인 완료 | AL-004 |
| draftM0 | 확인된 가상 제품당 원재료비 | AL-004 |
| deposited | 가상 예치 | 별도 지급 시뮬레이션 |
| paid | 가상 지급 실행 | 별도 지급 시뮬레이션 |

payment와 paid는 서로 다르다. payment는 업무 대조의 지급근거, paid는 시뮬레이션 명세의 실행 여부다. 혼합하면 시뮬레이션만으로 실제 지급 실적처럼 표시되므로 반드시 분리한다.

parseDemo는 잘못된 JSON·스키마·범위를 검증하고 초기 상태로 복구한다. 선행 발주 반영 없이 청구·지급근거가 완료된 저장 상태, 예치 없이 지급된 시뮬레이션 상태를 정리한다. localStorage 저장 실패 시 오류를 발생시키지만 사용자 친화적인 오류 복구 화면은 아직 보강 대상이다.

저장하지 않는 정보: 기존 등록 화면의 세부 입력·매핑, 신규 검토 확정 전 투입량·체크박스, 역할 선택, 실제 원문, 이력 전체. 요청은 같은 ID의 최신 내용으로 교체되므로 불변 감사 로그도 아니다.

### 4.10 P1 — 차액 지급 시뮬레이션 정정

기존 화면은 실제 체인이 연결되지 않았는데도 테스트넷 명칭과 가상 트랜잭션 해시를 보여줘 실제 실행으로 오해할 여지가 있었다.

이번에는 다음을 명시했다.

- 네트워크: 미연결, 향후 Kairos 검증 예정
- 단위: 원화 참고 차액 320,000원과 시뮬레이션 수량 320,000 DEMO 구분
- 거래 대상: AL-001 / 약정 버전 / calc-11 / PS-0001
- 지급자·수취인: 가상 구매·공급기업
- 절차: 명세 내용 확인 + 가상 예치 → 지급 버튼 활성화 → 완료 후 재실행 차단
- 완료 뒤 새로고침해도 동일 origin의 저장 상태가 유지되는 동안 실행 완료 상태 유지

브라우저 상태만으로 막는 중복 실행은 온체인 보안·동시성 보장과 다르다. 지갑 연결·Solidity 배포·주소·해시 생성·토큰 전송은 없다. 향후 별도 계약을 만들 때 명세 ID, 버전, commitment, 승인 주소, 토큰 금액, 지급 상태를 연결하는 방향을 설명한 것이다.

### 4.11 P2 — 서비스 소개·반응형·접근성 보완

- 소개 문구를 “여러 협력사의 단가 조정, 확인부터 반영까지 한곳에서”로 변경했다.
- 기존 약정 운영과 신규 약정 검토 체험을 각각 진입점으로 제공한다.
- 파일럿 신청처럼 읽히던 버튼을 데모 시작으로 정리하고 도입 설명은 협의안으로 표시한다.
- 내 업무 화면에서 거래 등록·전체 운영 화면으로 이동할 수 있게 했다.
- 900px 이상에서는 내 업무 최대 폭을 1120px로 넓히고 할 일 3열·약정 2열 배치를 적용한다.
- 760px 이하에서는 운영 메뉴를 가로 스크롤하고 표는 컨테이너 안에서 스크롤하도록 구성한다.
- 처리 시트의 Escape 닫기, Tab/Shift+Tab 순환, 닫힌 뒤 포커스 복귀를 보강했다.
- 기존 디자인을 유지하면서 검토 단계·증빙 영역에 추가 스타일을 적용했다. 전체 디자인을 새로 만든 것은 아니다.

반응형·인쇄·접근성 처리는 코드에 반영했으나 실제 브라우저의 시각·클릭 검증은 아직 완료하지 못했다.
