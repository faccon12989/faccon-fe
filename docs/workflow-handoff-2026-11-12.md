# 구매·공급기업 거래 흐름 연결 — 2026-11-12

## 결과와 범위

같은 AL-004 가상 거래를 구매기업 요청 → 공급기업 보완·공유 승인 → 구매기업 확인 → 발주·청구·지급근거 대조 → 증빙 조회까지 연결했습니다. 기업 대시보드를 시작점으로 유지하고 운영 콘솔은 상세 작업을 맡습니다.

현재 구현은 가상 데이터와 브라우저 저장소 기반 프런트엔드 데모입니다. 실제 로그인·기업별 서버 권한, 문서 업로드·전자서명, OCR/LLM 호출, 기관 접수, 블록체인·송금은 구현하지 않았습니다. 실제 기업자료를 입력하지 않습니다.

월별 조정은 이미 합의한 산식에 따라 계산합니다. 매월 양사의 새로운 승인을 받아야만 산식이 작동하도록 바꾸지 않았습니다. 최초 약정·변경·갱신 승인과 정기 계산 확인을 구분합니다.

## 상태·저장소 설계

- `faccon-role-v1`: sessionStorage. 탭별 구매/공급 역할과 선택 기업을 유지합니다.
- `faccon-work-v1`: localStorage. AL-004 자료 처리, ST-005 갱신, 발주·청구·지급근거, revision, 이력을 같은 브라우저 탭 사이에서 공유합니다.
- `faccon-setup-meta`: 초대·ERP 체험 설정 여부만 저장합니다. 실제 초대 메일을 발송하지 않습니다.
- `transition()`은 현재 역할·기업·단계·확인 여부와 revision을 검사합니다. 이전 화면의 오래된 revision은 거절합니다.
- 다른 PC·브라우저와는 데이터가 공유되지 않습니다. 동시 사용자 처리·원자성·접근통제는 후속 서버 구현 사항입니다. 역할 버튼은 인증 기능이 아닙니다.

## 직접 확인하는 순서

1. `app.html?role=buyer#/review`에서 가상 시나리오 초기화 후 AL-004 자료를 요청합니다.
2. 다른 탭에서 `app.html?role=supplier&supplier=S-04#/review`를 엽니다. 투입량 4kg를 입력하고 산정 결과를 미리 본 뒤 확인·제출합니다.
3. 구매 탭에서 사유를 적어 보완을 요청합니다. 공급 탭에서 다시 제출한 뒤 구매기업이 같은 버전을 확인합니다.
4. 반영 대조에서 구매기업 발주 등록 → 공급기업 청구 등록 → 구매기업 지급근거 등록을 순서대로 체험합니다.
5. 증빙에서 해당 기업·거래의 요약을 확인하고 CSV를 내려받습니다.
6. ST-005는 구매기업 갱신 제안 → 공급기업 S-05 동의 → 구매기업 최종 확정으로 체험합니다.
7. 시작하기 A/B 경로, 약정서 올리기 링크, 설정 저장, 모바일 기업 선택을 확인합니다.

## 팀원이 이어서 개발할 기준

`implementation-contract.md` 및 내부 요구사항 PA-SRS-001 v2.0의 FR/AI/NFR/BC ID를 사용합니다. 프런트 데모의 상태를 서버 인증/DB 상태로 옮기는 작업이 다음 단계입니다. 거래·문서 버전, 권한, 동시성, 정답 계산, 합성자료 OCR/LLM 평가를 각각 검증합니다.

외부 AI는 합성자료만 서버 어댑터를 통해 호출합니다. MonoRouter API 키·실제 회사 원문·내부 회의록은 공개 저장소에 넣지 않습니다. RAG는 관련 자료를 검색해 모델에 제공하는 구조이며 가중치 학습과 다릅니다.

로컬 변경이 없는 팀원은 저장소 폴더에서 다음 명령을 실행합니다.

```powershell
git switch main
git pull --ff-only origin main
npm.cmd run check
npm.cmd run dev
```

수정 중인 파일이 있다면 먼저 `git status`로 확인하고 자기 작업을 보존한 뒤 최신 main을 통합합니다. 충돌 시 reset/강제 덮어쓰기를 사용하지 않습니다. 이번 변경은 의존성 변경이 없어 재설치가 필요하지 않으며, 처음 받는 환경만 `npm.cmd install`을 실행합니다.
